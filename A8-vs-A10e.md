# Tab A8 vs A10e

**the tablet's column is filled** - every cell read from its own files; the how, with addresses, is in the [teardown](Tab-A8-teardown.md). the A10e column points at what's written up in [a10e-firmware](https://github.com/CassieFox23/a10e-firmware). the one piece still open - what the `red` boot state does downstream - is flagged in the teardown.

| question | A10e (SM-A102U) | Tab A8 (SM-X200) |
|---|---|---|
| chip family | Exynos | Unisoc UMS512 (`ro.soc.model=T618`) |
| can the bootloader be unlocked? | no - OEM unlocking isn't allowed on that unit | yes - done on two units from Download Mode, and `ro.boot.flash.locked` read back `0` after ([how-to](docs/lineageos-howto.md), step 5). the state is a 64-byte record in `miscdata` that the bootloader has the secure world judge; the permission switch is the last byte of `persistent` |
| what verified boot accepts | one Samsung key while locked | `vbmeta.img` is signed with one RSA-4096 key (a different one from the A10e's) and covers 11 partitions; the bootloader's signed certificate carries that key's SHA-256. on boot `lk` hands the image to the secure world (command `0x20`) and the boot state comes from that result; it also runs its own libavb, which checks the signature and feeds the kernel cmdline. unlocked, `boot`/`recovery` skip the secure-world check and the state goes orange; a locked failure sets the red state - what `red` then does downstream is the open piece, in the [teardown](Tab-A8-teardown.md#what-lk-does-about-verified-boot) |
| Treble level vs a current GSI | vendor level 3, below what the GSI ships | vendor level 5, VNDK 30, kernel 4.14.199 - the LineageOS 22.2 GSI ships a level 5 matrix and VNDK 30, so it fits |
| secure world | TEEGRIS | **Trusty** (Google's little-kernel TEE, Unisoc's port), confirmed three ways: the kernel defconfig (`CONFIG_TRUSTY=y`, no `CONFIG_TZDEV`), the `trustos` image (a Trusty TOS built Oct 2023, carrying keymaster, gatekeeper, RPMB storage and Widevine trusted apps), and what it does with the bootloader's two SMC commands - `0x33` authenticates a device-bound unlock token (AES-CBC under a key derived from the chip's hardware key, label `VerifiedBoot-UNLOCK`), `0x20` runs libavb (`avb_slot_verify`) inside the TEE. the stack is lk → BL31 monitor (`sml`) → Trusty. the SELinux fence holds: 0 permissive domains, no app domain reaches the `teetz_device` IPC node (mode `0660 system:system`, so Unix perms back it up, unlike the A10e's `0666`), and an app can `find` only the media HALs (Widevine, codec), never the key ones; keys go through `keystore` → keymaster as normal |
| extra flash gates | Knox Guard | Knox Guard here too: flashing is blocked when its state is `LOCKED` and a bitmask test of a flags global (`0x9f037540`) returns `0`, and unlocking is refused in `PRENORMAL`, `ACTIVE`, `LOCKED` or `ERROR` |
| ends up running | stock Android 9 | LineageOS 22.2 (Android 15) as a GSI on the stock 4.14.199 kernel - both read back right after the flash, Oct 2026. the Android 11 vendor is still stock going by what was flashed (only `system` and `recovery`) |

the A10e answers are short on purpose - the real ones, with addresses, are in its [teardown](https://github.com/CassieFox23/a10e-firmware/blob/master/A10e-teardown.md).
